# OBSCURA Public/Private Release Strategy

## Recommended repository split

| Repository | Visibility | Contents |
|---|---:|---|
| `obscura-metamaterial-observability-lab` | Public | README, synthetic showcase, sanitized outputs, collaboration forms |
| `obscura-core-private` | Private | Full notebook, solver, objectives, constitutive maps, calibration, raw telemetry |

Use **two separate repositories**. A branch, tag, release draft, or later deletion
inside one public repository is not a security boundary.

## Publish

- Project thesis and scientifically qualified claims
- Public threshold definitions
- General equations that are standard or intentionally disclosed
- Synthetic/read-only dashboard code
- Sanitized result summaries with hashes and provenance
- Screenshots or pre-rendered videos with visible disclosure labels
- Collaboration and citation instructions

## Keep private

- Full Colab notebook and monolithic Python source
- Exact constitutive response functions and all calibration constants
- Exact objective decomposition, weights, guards, rescue rules, and schedules
- Material-coordinate trajectories and high-resolution internal state
- Random-stream coupling, private seeds used for claimed experiments, and stress-bank internals
- Full raw NPZ/JSON exports before redaction
- API credentials, ngrok tokens, magic-access URLs, system prompts, and private tools
- Unpublished enabling implementation details that may matter to patent or trade-secret strategy

## Public result package

A real public result should be exported as a signed bundle containing only:

1. A configuration summary with sensitive fields removed.
2. A public telemetry CSV conforming to `docs/PUBLIC_TELEMETRY_SCHEMA.md`.
3. Static plots or videos generated from that public telemetry.
4. A manifest with SHA-256 hashes, run date, software version, and a statement
   that the bundle was generated by the private engine.
5. A limitations statement explaining that the export is not independently
   reproducible without controlled private access.

## Practical protection hierarchy

1. **Do not disclose enabling details.** This is the only reliable way to keep a
   trade-secret-like advantage.
2. Keep the complete engine in a private repository with minimal collaborators.
3. Use written collaboration terms before private disclosure.
4. Publish read-only outputs or operate the private solver behind an API rather
   than distributing it.
5. Register copyright if the legal and commercial value justifies it.
6. Consult qualified patent counsel before public disclosure if patent protection
   might be relevant.
7. Do not rely on Python obfuscation. It slows casual reading but is not a durable
   barrier.

This document is operational guidance, not legal advice.
